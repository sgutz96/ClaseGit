    ¿Qué es Git?

    Git es un sistema de control de versiones: guarda el historial de cambios de un proyecto para que puedas comparar versiones, recuperar código anterior y trabajar en equipo sin pisarte con otras personas.

    −Copiar la carpeta como "proyecto-final-v2-bueno" cada vez que algo funciona.
    −No saber qué cambió entre una versión y otra, ni quién lo hizo.
    +Guardar "fotografías" (commits) del proyecto con un mensaje que explica el cambio.
    +Volver a cualquier punto del historial cuando algo se rompe.

    Tres ideas clave

    • Instantáneas, no diferencias. Cada commit es una foto completa del estado del proyecto en ese momento.
    • Funciona en local. No necesitas internet para inicializar un repositorio ni para hacer commits.
    • Es distribuido. Cada copia del repositorio tiene el historial completo, no solo el servidor.

    El recorrido de un archivo

    Crear un repositorio: CMD, PowerShell y Git Bash

    Crear un repositorio local tiene dos partes: preparar la carpeta y sus archivos (esto sí cambia un poco entre consolas) y ejecutar git init (esto no cambia nunca).

    1
    Crea la carpeta del proyecto y entra en ella
    2
    Crea un archivo inicial — aquí es donde cambia el comando según la consola
    3
    Inicializa Git
    mkdir mi-proyecto
cd mi-proyecto
type nul > index.html
git init
    mkdir mi-proyecto
cd mi-proyecto
New-Item index.html
git init
    mkdir mi-proyecto
cd mi-proyecto
touch index.html
git init

    Crear el repositorio en GitHub (para conectarlo después)

    1. Entra a github.com y haz clic en New repository.
    2. Escribe un nombre, por ejemplo mi-proyecto.
    3. Si ya tienes el proyecto en tu computadora, no marques "Add a README" para evitar historiales que no coinciden.
    4. Haz clic en Create repository y copia la URL que aparece (termina en .git).
    CMD, PowerShell y Git Bash no son Git Son consolas: programas para escribir comandos. Git es el mismo programa en las tres; solo cambian comandos propios de cada shell, como crear archivos o carpetas.

    Conectarte a un repositorio remoto

    Conectar tu carpeta local con GitHub se hace con comandos de Git, así que son idénticos en CMD, PowerShell y Git Bash.

    Ya tienes un proyecto local

    Vincula tu carpeta existente a un repositorio vacío en GitHub:

    cualquier consola
    git branch -M main
git remote add origin https://github.com/usuario/mi-proyecto.git
git push -u origin main

    Quieres bajar un proyecto que ya existe

    Clona el repositorio: crea una copia local completa con todo el historial.

    cualquier consola
    git clone https://github.com/usuario/mi-proyecto.git
cd mi-proyecto

    Verifica la conexión

    cualquier consola
    $ git remote -v
origin  https://github.com/usuario/mi-proyecto.git (fetch)
origin  https://github.com/usuario/mi-proyecto.git (push)

    origin es solo un apodo: el nombre por defecto que Git le da a tu repositorio remoto.

    Nunca subas contraseñas ni claves Crea un archivo .gitignore desde el primer commit para excluir carpetas como node_modules/ o archivos como .env.

    Cómo hacer un commit

    Un commit es una fotografía identificable del proyecto en un momento dado, acompañada de un mensaje que explica qué cambió.

    1
    Revisa qué cambió
    git status
    $ git status
On branch main
Changes not staged for commit:
  modified:   index.html
    2
    Prepara los cambios (staging)
    git add
    git add index.html
# o, para agregar todo lo modificado:
git add .
    3
    Crea el commit
    git commit
    git commit -m "feat: agrega sección de bienvenida"
    4
    Revisa el historial
    git log
    $ git log --oneline
7b91c3d feat: agrega sección de bienvenida
a1e9f02 init: estructura inicial del proyecto

    git add

    Mueve cambios del directorio de trabajo al staging area. Todavía no crea el commit; solo lo prepara.

    git commit

    Guarda en el historial local todo lo que está en staging, junto con un mensaje que explica el cambio.

    Buenos mensajes de commit Usa un verbo claro y en presente: feat: para algo nuevo, fix: para una corrección, docs: para documentación. "cambios" o "asdf" no cuentan la historia del proyecto.

    Pull y push: subir y bajar cambios

    git push envía tus commits locales a GitHub. git pull trae los commits que existen en GitHub y no tienes en tu copia local. Son comandos de Git, así que se escriben igual en CMD, PowerShell y Git Bash.

    ↑ Push

    Sube tus commits locales al repositorio remoto. La primera vez conviene fijar el destino con -u; después basta con git push.

    ↓ Pull

    Descarga los commits nuevos del remoto y los integra en tu rama local. Internamente combina git fetch (traer información) con git merge (integrarla).

    git push -u origin main
git pull origin main
    git push -u origin main
git pull origin main
    git push -u origin main
git pull origin main
    Los tres paneles son idénticos, y eso es lo importante Push y pull son comandos de Git, no de la consola. La consola solo cambia cuando creas carpetas o archivos; una vez que escribes git, el comando es el mismo en cualquier sistema.
    Si el push es rechazado GitHub tiene commits que tú no tienes en local. Ejecuta git pull primero, resuelve cualquier conflicto y vuelve a intentar git push.

    Ramas: trabajar sin romper lo que ya funciona

    Una rama (branch) es una línea de desarrollo independiente. Permite probar cambios sin afectar main hasta que decides integrarlos.

    commits en main commits en la rama commit de fusión (merge)
    git bash
    # ver las ramas existentes
git branch

# crear una rama nueva
git branch feature/formulario

# cambiarte a esa rama
git checkout feature/formulario

# crear y cambiar en un solo paso (forma moderna)
git switch -c feature/formulario

# ... trabajas, agregas y haces commits en esta rama ...

# volver a main e integrar los cambios
git checkout main
git merge feature/formulario

# borrar la rama una vez fusionada
git branch -d feature/formulario
    Si hay un conflicto de fusión Git marca el archivo con <<<<<<<, ======= y >>>>>>> cuando dos ramas cambiaron la misma línea. Edita el archivo para dejar el contenido correcto, elimina los marcadores y crea el commit con git add . y git commit.

    GitHub Pages, Vercel y otras formas de publicar

    Un repositorio con tu sitio no está publicado hasta que alguna plataforma sirve esos archivos como página web. Estas son las más comunes para proyectos con HTML, CSS y JavaScript.

    📄

    GitHub Pages

    Publica sitios estáticos directamente desde un repositorio de GitHub, sin salir de la plataforma.

    1. Sube tu proyecto con un index.html en la raíz.
    2. Entra a Settings → Pages del repositorio.
    3. Elige la rama (normalmente main) y la carpeta de origen.
    4. GitHub entrega una URL del tipo usuario.github.io/repositorio.
    ▲

    Vercel

    Plataforma de despliegue enfocada en frontend, con integración directa a GitHub y una URL por cada rama o pull request.

    1. Crea una cuenta en vercel.com con tu cuenta de GitHub.
    2. Haz clic en Add New → Project e importa tu repositorio.
    3. Confirma la configuración de build y haz clic en Deploy.
    4. Cada git push genera un nuevo despliegue automáticamente.
    PlataformaIdeal paraDominio propio
    GitHub PagesSitios estáticos simples, portafolios, documentaciónSí
    VercelProyectos con frameworks (React, Next.js, Vite)Sí

    README.md y README.mdx

    La documentación es parte del proyecto. Un README explica qué es, cómo se instala, cómo se usa y cómo contribuir. .md es Markdown; .mdx combina Markdown con componentes JSX cuando la plataforma de documentación lo admite.

    ¿Qué es README.md?

    Es un archivo de documentación en formato Markdown. En un repositorio de GitHub suele colocarse en la raíz y GitHub lo muestra como la portada documental del proyecto.

    • Presenta: nombre, propósito y contexto.
    • Explica: instalación, uso y comandos.
    • Orienta: estructura, contribución y autoría.

    ¿Qué es README.mdx?

    MDX permite escribir Markdown e insertar componentes JSX. No es simplemente “un Markdown con otra extensión”: necesita una herramienta que procese MDX y un entorno compatible con componentes.

    • Útil en documentación interactiva.
    • Permite reutilizar componentes de una interfaz.
    • En GitHub, la compatibilidad con archivos MDX no equivale a que se rendericen como un README estándar.

    Glosario

    Repositorio
    Carpeta de proyecto donde Git lleva el registro de cambios.
    Commit
    Punto guardado en el historial, con un mensaje que explica el cambio.
    Staging area
    Zona intermedia donde se preparan los cambios antes de confirmarlos.
    Remoto
    Copia del repositorio alojada en un servicio como GitHub.
    Rama (branch)
    Línea de desarrollo independiente que parte de un commit.
    Merge
    Integrar los cambios de una rama en otra.
    Conflicto
    Situación en la que dos ramas cambiaron la misma línea y Git necesita ayuda para decidir cuál conservar.
